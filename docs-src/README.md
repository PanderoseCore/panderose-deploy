# docs-src — developer docs source

**Read [`PLATFORM-REVIEW.md`](./PLATFORM-REVIEW.md) before making any
architecture or access-control change here** — it's the audit of every
decision behind this system after a real incident (internal content
leaked, unauthenticated; see ADR 0006) and the standard this system is
now held to. Internal docs are currently disabled by design (§5 of that
review) — do not re-enable them without following its roadmap.

The Docusaurus **source** for panderose.com/docs. It builds to `../docs`
(repo root) — that's **generated, committed** static output, never
hand-edited. See
[ADR 0003](./content/internal/standards/adrs/0003-built-output-committed.md)
for why the build output is committed here instead of built downstream,
and
[ADR 0002](./content/internal/standards/adrs/0002-single-swa-resource.md)
for the hosting model.

Two doc instances sharing one theme/nav shell:

- **Public** (`content/public/`) — served at `panderose.com/docs/`.
  Guides + API reference for anything Panderose publishes externally.
- **Internal** (`content/internal/`) — served at
  `panderose.com/docs/internal/`. Engineering standards, cyber assessment
  infrastructure notes, repo architecture, and the Cambium-backed
  opportunity/ontology program. Gated via the root
  `staticwebapp.config.json`'s `allowedRoles` on that route, and excluded
  from `robots.txt`/`sitemap.xml` — **the routing rule ships here, but
  someone with Azure portal access still has to confirm an identity
  provider and role assignment are actually configured** before this is
  access-controlled in production, not just routed.

API reference pages are never hand-written — they're generated at build
time from OpenAPI specs in `specs/public/` and `specs/internal/` via
[`docusaurus-plugin-openapi-docs`](https://github.com/PalmettoSoftware/docusaurus-openapi-docs).
See [`specs/README.md`](./specs/README.md) for how a FastAPI service is
expected to keep its spec in sync here.

## Local development

```bash
npm install
npm run gen-api-docs:all   # (re)generate API reference from specs/
npm start                  # dev server, hot reload — http://localhost:3000/docs/
```

## Regenerating the committed `docs/` output

```bash
npm run build:ci                     # from docs-src/: gen-api-docs + build -> build/
cd .. && ./scripts/package-site.sh   # from repo root: does the above AND
                                      # replaces ../docs with the fresh output
git diff --stat docs                 # review before committing
```

`.github/workflows/build-docs.yml` does the same on every push to `main`
that touches `docs-src/**`, committing the result automatically. Either
way, `docs/` at the repo root should always match what `docs-src/` would
currently build — if it doesn't, something didn't get regenerated.

## Adding content

- Public guide/reference page → add a Markdown/MDX file under
  `content/public/`.
- Internal-only page → same, under `content/internal/`.
- Both sidebars are filesystem-autogenerated (see `sidebarsPublic.js` /
  `sidebarsInternal.js`) — just add the file, no sidebar config needed
  unless you want manual ordering/grouping.
- New service's API reference → don't write it by hand; land its OpenAPI
  spec in `specs/public/` or `specs/internal/` per
  [`specs/README.md`](./specs/README.md).
- Non-obvious technical decision about this docs site itself → add an ADR
  under `content/internal/standards/adrs/`.
- Docusaurus strips numeric `NNNN-` prefixes from generated slugs/permalinks
  (an ADR file named `0004-foo.md` is linked as `.../foo`, not
  `.../0004-foo`) — keep that in mind when cross-linking ADRs.
